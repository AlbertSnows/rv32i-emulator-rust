Privileged mode / CSR conformance (item #11) -- S-mode, delegation, and
what's already here

--- why ---

Everything built so far runs entirely in M-mode. That's fine for
bare-metal firmware, but an actual OS kernel runs in S-mode, under an
M-mode firmware layer (think: OpenSBI underneath Linux) -- and the plan
doc's own framing is right that this is a foundational item.
"an S-mode kernel under an M-mode firmware runs on nothing
else." Without S-mode CSRs, SRET, and trap delegation, there's no
mechanism for control to ever reach or return from a less-privileged
mode in a way software actually relies on.

Source: docs/books/riscv_privleged.pdf (RISC-V Instruction Set Manual,
Volume II: Privileged Architecture) -- Section 3.1.8 (Machine Trap
Delegation), pp. 42-43, and Chapter 12 (Supervisor-Level ISA),
pp. 112-120.

--- 0. what this codebase already has ---

- `CPUMode` (U/S/M) already exists (src/definitions/cpu/cpu_definition.rs),
  with conversions to/from the 2-bit privilege encoding (PRIV_U/S/M).
- `TrapCause` already distinguishes `EnvironmentCallFromUMode` /
  `EnvironmentCallFromSMode` / `EnvironmentCallFromMMode` separately.
  the current-mode tracking this all depends on is already wired
  through the trap path.
- M-mode CSR state exists and works: mstatus, mtvec, mepc, mcause,
  mtval, mcycle, minstret, mie, mip (src/definitions/cpu/csr.rs), plus
  MRET (src/instructions/i/system.rs) and mstatus's MPP
  (bits 12:11)/MPIE (bit 7) fields (src/definitions/masks.rs).
- None of the S-mode CSRs, SRET, or medeleg/mideleg exist yet, this
  doc is entirely about that gap.

--- 1. the key simplification: sstatus/sie/sip aren't new storage ---

From the spec (Chapter 12, Supervisor-Level ISA intro):

  "The sstatus register is a subset of the mstatus register. In a
  straightforward implementation, reading or writing any field in
  sstatus is equivalent to reading or writing the homonymous field in
  mstatus."

Same relationship holds for sie/mie and sip/mip (S-mode sees a masked
subset of the M-mode register's bits). This means `CSRState` does
*not* need new `sstatus`/`sie`/`sip` fields; it needs sstatus/sie/sip
*reads and writes* implemented as masked accessors into the existing
mstatus/mie/mip storage. Concretely, sstatus exposes (at minimum, for
what this codebase needs next): SIE (bit 1), SPIE (bit 5), SPP (bit 8).
the S-mode-visible slice of the same bits MPIE (bit 7) and MPP
(bits 12:11) already occupy for M-mode. This is the same
xIE/xPIE/xPP "two-level stack" pattern already implemented for M-mode,
just at the S level:

  "xPIE holds the value of the interrupt-enable bit active prior to
  the trap, and xPP holds the previous privilege mode... When a trap
  is taken from privilege mode y into privilege mode x, xPIE is set to
  the value of xIE; xIE is set to 0; and xPP is set to y."
  (Section 3.1.6.1, p.32)

sepc/scause/stval/sscratch, by contrast, genuinely are separate
storage from their M-mode counterparts (a trap delegated to S-mode
must leave mepc/mcause/mtval untouched, see delegation below), add
those as real new fields on `CSRState`.

--- 2. new CSR addresses (Section 2.2.2, Table 5, p.17 -- "Currently
    allocated RISC-V supervisor-level CSR addresses") ---

  0x100  sstatus    (masked view into mstatus, see above)
  0x104  sie        (masked view into mie)
  0x105  stvec      (real storage -- S-mode's own trap vector base)
  0x140  sscratch   (real storage)
  0x141  sepc       (real storage)
  0x142  scause     (real storage)
  0x143  stval      (real storage)
  0x144  sip        (masked view into mip)

Plus two *machine*-level CSRs that control delegation itself:

  0x302  medeleg    (real storage, new)
  0x303  mideleg    (real storage, new)

--- 3. trap delegation (medeleg/mideleg) ---

By default every trap goes to M-mode. Setting bit N in medeleg means:
if that specific synchronous exception (N = the same code
TrapCause::mcause_code() already returns) occurs while executing in
S-mode *or* U-mode, it's delivered directly to the S-mode handler
instead. mideleg works the same way for interrupts, with bit positions
matching mip's layout (e.g. bit 5 = supervisor timer interrupt).

When a trap *is* delegated to S-mode (Section 3.1.8, p.42):
  - scause <- the trap cause
  - sepc <- the address of the trapping instruction
  - stval <- the exception-specific value (same role mtval plays for
    M-mode traps)
  - mstatus.SPP <- the privilege mode active when the trap occurred
  - mstatus.SPIE <- the current value of mstatus.SIE
  - mstatus.SIE <- 0
  - mcause, mepc, mtval, and mstatus's MPP/MPIE fields are explicitly
    **not** touched by a delegated trap -- only the M-mode path writes
    those.

One hard rule to get right, since it's easy to get backwards: **traps
never move to a less-privileged mode than where they occurred.** If
M-mode software hits an illegal instruction, it traps in M-mode
regardless of what medeleg says. delegation only ever routes a trap
*at or below* S-mode down to S-mode, never up.
refer: (Section 3.1.8, p.43:
"if M-mode has delegated illegal-instruction exceptions to S-mode, and
M-mode software later executes an illegal instruction, the trap is
taken in M-mode, rather than being delegated.")

So the existing trap-dispatch logic (wherever it currently
unconditionally goes to the M-mode path) needs a branch:
if the trapping mode is S or U *and* the
corresponding medeleg/mideleg bit is set, take the S-mode path above
instead of the existing M-mode one. If the trapping mode is M, or the
bit is clear, existing behavior is unchanged.

--- 4. SRET ---

Mirrors MRET exactly (same xRET rule, Section 3.1.6.1, p.32, already
partially quoted above), just one privilege level down and with a
different opcode:

  MRET funct12 = 0x302  (already implemented: 0x30200073)
  SRET funct12 = 0x102  (new: 0x10200073)

Both are SYSTEM-opcode (0b1110011), rs1=0, rd=0, funct3=0 -- the
existing `SystemOp`/`parse_system_inst` in src/instructions/i/system.rs
already has the shape for this; SRET is a sibling match arm to MRET,
not new architecture. Semantics, substituting S for M throughout
inst_i_mret's existing logic:

  - mstatus.SIE <- mstatus.SPIE
  - privilege mode <- mstatus.SPP
  - mstatus.SPIE <- 1
  - mstatus.SPP <- least-privileged supported mode (U, here)
  - pc <- sepc

One new legality check MRET didn't need: SRET is illegal (traps as an
illegal instruction) if executed from a mode with insufficient
privilege to use it, i.e. from U-mode, or from S-mode when
mstatus.TSR=1 (trap-SRET, meant for hypervisor emulation -- out of
scope here, so treat TSR as hardwired 0 for now and just check
current_mode != U).

--- 5. what needs to change in this codebase ---

- src/definitions/cpu/csr.rs: add real storage fields for stvec,
  sscratch, sepc, scause, stval, medeleg, mideleg to `CSRState`
  (initialized to 0 in build_csr_state); add sstatus/sie/sip
  read/write as masked-accessor methods over mstatus/mie/mip rather
  than new fields (see section 1).
- src/core.rs (wherever handle_trap currently lives): branch on
  medeleg/mideleg + trapping mode before choosing the M-mode vs
  S-mode trap-entry sequence (section 3 above).
- src/instructions/i/system.rs: new `SystemOp::SRet` variant, parse
  arm for funct12=0x102, and `inst_i_sret` alongside the existing
  `inst_i_mret` -- same shape, S-level fields, plus the
  current_mode != U legality check MRET doesn't need.
- src/definitions/trap_cause.rs: no new variants needed -- the
  existing mcause_code() values are exactly what medeleg's bit indices
  key off of.
