      16  Double trap -- confirmed wanted. Mechanism per Section 3.1.6.2
          "Double Trap Control in mstatus Register" (p.33) and Chapter 10
          "Smdbltrp" Double Trap Extension (p.96): occurs when a new trap
          arrives while the trap handler is still in a non-reentrant state
          (hasn't yet saved recovery state) -- called an "unexpected trap."
          Without the Smrnmi extension (not needed here), the spec's defined
          response is exact: "the hart enters a critical-error state...
          ceasing execution, disabling all interrupts... and asserting a
          critical-error signal to the platform." A minimal version: track
          whether we're already inside trap handling; if a second trap
          arrives before that's cleared, treat it as unrecoverable (halt) --
          close to what this emulator already does by default for
          everything else, so this is a small addition once the base
          mechanism (item #3) exists, not a big new piece.


    Interrupts (the ENTIRE separate Interrupt=1 half of Table 16, not just
    individual missing codes) -- will eventually be needed, for a
    fundamental reason: Linux's scheduler relies on preemptive multitasking
    driven by periodic timer interrupts (codes 5 Supervisor timer / 7
    Machine timer -- mechanism is mtime/mtimecmp, Section 3.2.1, p.59).
    External interrupts (Supervisor/Machine external) will matter once real
    device I/O (console, disk) exists. Software interrupts (inter-hart
    signaling) can stay deferred indefinitely -- this project is single-hart
    and multi-hart seems out of scope even for "rudimentary."

    xIE (global interrupt-enable bit, e.g. MIE for M-mode) -- lives in
    mstatus alongside MPP, right next to it (Section 3.1.6.1, p.31-32).
    Same trap-entry moment that sets MPP also clears xIE ("xIE is set to
    0"); MRET/SRET restore it from xPIE the same way they restore mode from
    xPP. Noted here because it surfaced while designing item #4's MPP/MRET
    work, but it has zero functional effect until interrupts (above) exist
    -- nothing in this emulator checks it yet. Don't implement the check
    now; just don't forget it's part of the same mstatus register once
    interrupts land.


[ ] 4. Privilege levels (M/S/U mode) aren't modeled at all.
    Real RISC-V defines multiple execution modes: Machine (M, most
    privileged, always present), Supervisor (S, typically an OS kernel),
    and User (U, application code). Per item #2's spec quote, each CSR has
    a *minimum* privilege level required to access it, encoded in the
    address itself (csr[9:8]). This emulator has no concept of "what mode
    is the CPU currently in" -- there's no mode-switching, no state
    tracking which mode is active -- so even if we wanted to enforce this
    second layer of CSR access control, there's currently nothing to check
    it against.

[ ] 5. CSRs are all generic, meaningless storage right now.
    CsrState is a flat [u32; 4096] -- reading or writing any address just
    touches a plain array slot, nothing more. On real hardware, specific
    addresses have predefined meaning and behavior: reading the `cycle`
    CSR returns a live, continuously-updating counter (not a static stored
    value); specific bits of `mstatus` control whether interrupts are
    enabled and actually affect CPU behavior when changed; etc. None of
    that exists here -- every CSR address behaves identically, as inert
    storage, regardless of which "real" CSR it's supposed to represent.
