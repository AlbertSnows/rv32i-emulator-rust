      16  Double trap -- confirmed wanted. Mechanism per Section 3.1.6.2
          "Double Trap Control in mstatus Register" (p.33) and Chapter 10
          "Smdbltrp" Double Trap Extension (p.96): occurs when a new trap
          arrives while the trap handler is still in a non-reentrant state
          (hasn't yet saved recovery state) -- called an "unexpected trap."
          Without the Smrnmi extension (not needed here), the spec's defined
          response is exact: "the hart enters a critical-error state...
          ceasing execution, disabling all interrupts... and asserting a
          critical-error signal to the platform." A minimal version: track
          whether we're already inside trap handling; if a second trap
          arrives before that's cleared, treat it as unrecoverable (halt) --
          close to what this emulator already does by default for
          everything else, so this is a small addition once the base
          mechanism (item #3) exists, not a big new piece.

    Interrupts (the ENTIRE separate Interrupt=1 half of Table 16, not just
    individual missing codes) -- will eventually be needed, for a
    fundamental reason: Linux's scheduler relies on preemptive multitasking
    driven by periodic timer interrupts (codes 5 Supervisor timer / 7
    Machine timer -- mechanism is mtime/mtimecmp, Section 3.2.1, p.59).
    External interrupts (Supervisor/Machine external) will matter once real
    device I/O (console, disk) exists. Software interrupts (inter-hart
    signaling) can stay deferred indefinitely -- this project is single-hart
    and multi-hart seems out of scope even for "rudimentary."

[ ] 3. No trap/exception handling exists -- this is the bigger missing piece.
    On real hardware, things like an illegal instruction, a misaligned
    memory access, or an `ecall` don't just fail quietly -- they "trap":
    execution jumps to a handler address, and some state gets recorded so
    the handler (and potentially the trapped-from code, afterward) knows
    what happened. Three CSRs are central to this on real RISC-V:
      - mtvec ("machine trap vector"): holds the address the CPU jumps to
        when a trap occurs -- like an interrupt/exception handler address.
      - mepc ("machine exception program counter"): saves the PC at the
        moment of the trap, so execution can potentially resume afterward.
      - mcause ("machine cause"): a code saying *why* the trap happened
        (illegal instruction, misaligned access, ecall, etc).
    None of this exists here. Right now, every failure in this codebase
    (bad memory access, unrecognized opcode, and soon illegal CSR writes)
    just returns Err(String) -> bubbles up through core::step -> gets
    printed and the whole emulator halts (see main.rs). That's a reasonable
    simplification for a toy emulator, but it's not how real trap handling
    works, and it means mtvec/mepc/mcause would just be more generic,
    inert storage slots even once item #2 exists -- there's no mechanism
    that would actually populate them or redirect execution to mtvec's
    address.

[ ] 4. Privilege levels (M/S/U mode) aren't modeled at all.
    Real RISC-V defines multiple execution modes: Machine (M, most
    privileged, always present), Supervisor (S, typically an OS kernel),
    and User (U, application code). Per item #2's spec quote, each CSR has
    a *minimum* privilege level required to access it, encoded in the
    address itself (csr[9:8]). This emulator has no concept of "what mode
    is the CPU currently in" -- there's no mode-switching, no state
    tracking which mode is active -- so even if we wanted to enforce this
    second layer of CSR access control, there's currently nothing to check
    it against.

[ ] 5. CSRs are all generic, meaningless storage right now.
    CsrState is a flat [u32; 4096] -- reading or writing any address just
    touches a plain array slot, nothing more. On real hardware, specific
    addresses have predefined meaning and behavior: reading the `cycle`
    CSR returns a live, continuously-updating counter (not a static stored
    value); specific bits of `mstatus` control whether interrupts are
    enabled and actually affect CPU behavior when changed; etc. None of
    that exists here -- every CSR address behaves identically, as inert
    storage, regardless of which "real" CSR it's supposed to represent.

[ ] 6. ecall is a complete no-op right now.
    Currently, in i/system.rs: `SystemOp::ECall => Ok(ExecutionSignal::Continue)`.
    On real RISC-V, `ecall` is how a program requests something from its
    execution environment -- e.g. in an OS context, it's how user-space
    code asks the kernel to do something on its behalf (a "syscall"),
    typically by putting a syscall number and arguments in specific
    registers before executing ecall, and having the OS's trap handler
    read those registers and act. Here, ecall doesn't trap, doesn't invoke
    any handler, and doesn't look at any registers -- it just continues as
    if nothing happened. This is tied to item #3 (trap handling) -- ecall
    IS a trap, specifically an "environment call" trap, so it can't really
    be implemented properly until traps exist.

[ ] 7. FENCE instruction -- not implemented at all, not even parsed.
    FENCE is part of the RV32I base ISA (separate opcode, 0b0001111 --
    confirmed via grep that no such constant exists in op_codes.rs and
    nothing in src/ references FENCE at all). It's a memory-ordering
    instruction: it tells the CPU "make sure memory operations before this
    point are visible before memory operations after this point proceed."
    This matters on real hardware with out-of-order execution, multiple
    cores, or memory-mapped I/O, where operations can otherwise be
    reordered in ways that would break correctness. This emulator is
    single-threaded and executes strictly in-order with no reordering at
    all, so a correct FENCE implementation here would legitimately just be
    a no-op that returns Continue -- same shape as EBREAK/ECALL's stubs.
    It's not hard to add; it's just been completely absent from decoding
    up through execution this whole time.
